# Documentation style

Use this guide for the README, setup instructions, user guides, API examples, release notes, and project messages.

## Principles

- Put the answer or action first.
- Write for the reader's task, not to sound impressive.
- Prefer common words, active voice, and concrete verbs.
- Keep paragraphs focused. Use a heading when it helps readers find information.
- Use the same name for the same feature or concept throughout the project.
- Use lists and tables when they make information easier to scan; do not force them into every section.
- Keep limitations, prerequisites, failure cases, and next steps visible.
- Keep the tone appropriate to the audience. Plain language does not mean careless or overly casual language.

## Accuracy rules

- Do not invent capabilities, compatibility, performance claims, dates, or test results.
- Keep commands, paths, code, configuration keys, API fields, links, and quoted text exact unless the change requires editing them.
- Distinguish a feature that is included from an optional integration that must be installed separately.
- If a step has not been tested, say so. Do not present an example as verified behavior.
- Preserve the meaning and important details when shortening a section.

## Review checklist

- Can a reader find the main answer quickly?
- Does each paragraph add useful information?
- Are any introductions, transitions, or conclusions repeating what the reader already knows?
- Are claims supported by the project or a cited source?
- Are setup steps and examples consistent with the current code?
- Are warnings and limitations easy to find?
- Does the text read naturally without forced contrasts, formulaic triads, inflated language, or unnecessary punctuation?
